# 06 — Finance and Billing

## 1. Scope

Fee catalogue, invoice generation, payment collection (virtual account, QRIS,
manual transfer, cash), reconciliation, arrears management, discounts/waivers,
refunds, and the double-entry ledger everything settles into.

This module carries the company's second revenue engine. Correctness here is
non-negotiable: **every rupiah must be traceable from parent to school bank account.**

## 2. Entities

```

         subtotal, discount, total, paid, status)

```

### 2.1 Currency columns

Every money column above is `DECIMAL(18,2)` (`core.MoneyField`). `fee_types`,
`invoices`, `payments`, `refunds` and `ledger_entries` each carry a
`currency CHAR(3)`. An invoice's currency is fixed at issue and inherited by its
lines, allocations and journals. See spec 16.

## 3. Fee and invoice generation

| ID | Requirement |
|---|---|
| `FIN-001` | A fee plan MUST be assignable to a grade level, a class, or an individual student; individual assignment overrides class, which overrides grade. |
| `FIN-002` | Monthly SPP invoices MUST be generated by a scheduled job on `invoice_generation_day` (default: 25th, for the following month), per school, per academic year. |
| `FIN-003` | Generation MUST be idempotent: re-running for the same (student, fee_type, period) MUST NOT create a second invoice. |
| `FIN-004` | Invoice numbering MUST be sequential per school per year, gapless, format `INV/{school_code}/{YYYY}/{NNNNNN}`. Numbers are allocated in a transaction; a failed invoice consumes no number. |
| `FIN-005` | Students with status ≠ `ACTIVE` MUST be excluded from generation. |
| `FIN-006` | Sibling discount MUST be supported as a rule: Nth child of the same financial guardian receives X% off SPP, configurable per school. |
| `FIN-007` | Discounts and waivers above `foundation.approval_threshold` MUST enter `PENDING_APPROVAL` and take effect only on approval (see 03 §3). |
| `FIN-008` | A generation run MUST produce a preview/dry-run report (count, total, exclusions with reasons) reviewable before commit. |
| `FIN-008b` | An invoice's currency MUST be the school's `base_currency` unless the student has an explicit `billing_currency` override from the school's `billing_currencies`. Mixing currencies on one invoice raises `CURRENCY_MISMATCH`. |
| `FIN-008c` | IDR invoice totals MUST round to Rp 100 with an explicit `PEMBULATAN` line (`CUR-019`). |
| `FIN-009` | Invoice status machine: `DRAFT → ISSUED → (PARTIALLY_PAID) → PAID`, plus `OVERDUE`, `CANCELLED`, `WRITTEN_OFF`. `OVERDUE` is derived from `due_date`, not stored as a terminal state. |

## 4. Payments

| ID | Requirement |
|---|---|
| `FIN-010` | Supported methods: bank **virtual account** (BCA, Mandiri, BRI, BNI, Permata), **QRIS**, **manual bank transfer with proof upload**, and **cash at school**. |
| `FIN-011` | Each student MUST have a stable per-school VA number where the bank supports it; otherwise a per-invoice VA with expiry. |
| `FIN-012` | Gateway integration MUST be abstracted behind a `PaymentProvider` interface with Midtrans and Xendit implementations; switching provider MUST NOT require domain changes. |
| `FIN-013` | Webhooks MUST verify signature, be idempotent on `external_id`, and be processed even if received out of order (settlement before authorisation). |
| `FIN-013b` | A payment MUST only be allocatable to invoices of the same currency. |
| `FIN-014` | Payments MUST be allocatable across multiple invoices/lines; default allocation is oldest-invoice-first, overridable by finance officer. |
| `FIN-015` | Overpayment MUST create a credit balance on the student, usable against future invoices, never silently absorbed. |
| `FIN-016` | Underpayment MUST set `PARTIALLY_PAID` and show the exact remaining balance to the parent. |
| `FIN-017` | The convenience fee MUST be configurable as `ABSORBED_BY_SCHOOL` or `PASSED_TO_PARENT`; when passed on, it MUST be displayed as a separate line before the parent confirms. |
| `FIN-018` | Manual transfer proof MUST enter `PENDING_VERIFICATION`; a finance officer confirms or rejects with reason. Confirmation is audited. |
| `FIN-019` | Cash receipt MUST produce a printable/downloadable receipt with a unique receipt number and the receiving officer's name. |
| `FIN-020` | A payment MUST NOT be deletable. Reversal is a `refunds` record plus offsetting ledger entries. |

## 5. Ledger

| ID | Requirement |
|---|---|
| `FIN-021` | Every financial event MUST write balanced double-entry `ledger_entries` — sum debits = sum credits per journal **per currency**, exactly 0.00. |
| `FIN-022` | Minimum chart of accounts: `1100 Cash/Bank`, `1200 Accounts Receivable`, `2100 Unearned Tuition`, `2200 Student Credit Balance`, `4100 Tuition Revenue`, `4200 Other Revenue`, `5100 Payment Fees`, `6xxx Payroll` (see 11). |
| `FIN-023` | Journal postings: invoice issued → Dr AR / Cr Unearned; period recognised → Dr Unearned / Cr Revenue; payment settled → Dr Cash, Dr Fee Expense / Cr AR. |
| `FIN-024` | A daily reconciliation job MUST compare gateway settlement reports against `payments` and produce a discrepancy list; unmatched items MUST be actionable, not just logged. |
| `FIN-025` | Period close MUST be supported: closing a month locks ledger entries for that period; post-close corrections go to the next open period. |

## 6. Arrears

| ID | Requirement |
|---|---|
| `FIN-025b` | The arrears ladder, invoice generation, reconciliation and period-close all run as cron management commands (see 01 §5.1); none may rely on a background worker. |
| `FIN-026` | Automated reminder ladder, configurable per school: T-3 days before due, due date, T+3, T+7, T+14, T+30 (see 13). |
| `FIN-027` | Reminders MUST stop immediately when the invoice is paid in full — checked at send time, not at schedule time. |
| `FIN-028` | Reminder channel priority: WhatsApp → push → SMS. Content MUST include student name, period, amount, due date and a payment deep link. |
| `FIN-029` | AR aging report by student, class and school with 0–30/31–60/61–90/90+ buckets. |
| `FIN-030` | Payment plans (installments) MUST be supported: split an invoice into N dated installments; the parent sees a schedule, reminders follow the installment dates. |
| `FIN-031` | Write-off MUST require foundation approval and post `Dr Bad Debt / Cr AR`. |

## 7. Refunds

| ID | Requirement |
|---|---|
| `FIN-032` | Refund requests capture amount, reason, destination bank account and require approval per threshold policy. |
| `FIN-033` | Refund execution MUST be recorded with proof (gateway payout id or transfer reference) and notify the guardian. |
| `FIN-034` | Partial refunds MUST be supported; cumulative refunds MUST never exceed the settled payment amount. |

## 9. Acceptance criteria

1. Running generation twice for period `2026-10` produces exactly one invoice per student.
2. A partial VA payment of Rp 500,000 against a Rp 750,000 invoice yields `PARTIALLY_PAID`, remaining Rp 250,000, and balanced ledger entries.
3. A duplicate webhook with the same `external_id` is a no-op returning 200.
4. A settlement webhook arriving before its authorisation webhook still results in exactly one `SETTLED` payment.
5. Paying an invoice at 09:00 cancels the T+7 reminder scheduled for 09:30.
6. Every journal in `ledger_entries` sums debits = credits (enforced by a DB constraint or check job).
7. A Rp 6,000,000 waiver cannot take effect without foundation approval.
8. Every money value in the finance API responses is a JSON **string** at 2dp with a sibling `currency`.
9. Running `generate_invoices` twice in the same cron minute — the second run exits immediately on the advisory lock.
