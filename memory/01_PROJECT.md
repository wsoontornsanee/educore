# 01_PROJECT — Current Status & Living State

## 1. Project Overview
- **Name:** EduCore (Sistem Operasi Sekolah)
- **Target Institutions:** Indonesian schools of all types (sekolah negeri, sekolah swasta, madrasah, pesantren modern, SPK/National-Plus).
- **Core Stack:** Python 3.12, Django 5.x LTS monolith, MySQL 8.0, cron background scheduling, HTMX + Tailwind for web, React Native (Expo) for mobile.
- **Design System:** `spec/17-design-system-and-ui.md` (Plus Jakarta Sans + IBM Plex Sans/Mono, Merah flag-saturated `#C8102E`, institutional square 0px radii, 5 mandatory screen states).

## 3. Retrospectives & Key Architectural Discoveries

1. **Fail-Closed Tenancy:** `TenantManager.get_queryset()` was designed to return `.none()` if no active thread-local `foundation_id` is set. This guarantees zero cross-tenant data leaks if an endpoint or command forgets to scope context.
2. **Float Rejection in MoneyField:** Validating at both `to_python` and `get_prep_value` prevents any accidental Python `float` assignment, ensuring all financial calculations retain strict decimal precision (`CUR-005`).
3. **Database Driver Agnosticism for Dev/CI:** Integrated `pymysql.install_as_MySQLdb()` fallback in `educore/__init__.py` allowing seamless development on platforms without precompiled C-wheels for `mysqlclient`, alongside `docker-compose.yml` for local MySQL 8.
4. **Advisory Lock Safety:** Named MySQL locks (`GET_LOCK`) cleanly prevent overlapping cron job executions across horizontal app nodes. Fallback in-memory mutex allows offline tests to verify locking semantics without external services.
5. **Worker Task Draining:** `drain_tasks` uses `SELECT ... FOR UPDATE SKIP LOCKED` where supported (MySQL 8) and safely executes tasks under the task's originating `foundation_id` context.
6. **Swappable User Model in Initial Migration:** Django requires custom `AUTH_USER_MODEL` to be declared in the app's initial migration (`0001_initial.py`) because `admin.0001_initial` depends on `('identity', '__first__')`. Attempting to introduce `User` in `0002_...` triggers a lazy reference `ValueError` in `admin.LogEntry.user`.
7. **UU PDP Person PII Vault Isolation:** Identity-bearing PII (`nik`, `dob`, `gender`, `address`) is stored exclusively in `persons` (`Person` model), while `users` (`User` model) holds only auth credentials, phone/email identifiers, and account lockout security fields.
8. **RBAC Scope Isolation & Fail-Closed Guardrails:** Roles are assigned at either `FOUNDATION` scope or `SCHOOL` scope. `HasRequiredPermission` strictly fails closed if a view forgets to define `required_permission` (`IAM-010`), and school-scoped roles cannot access sibling schools (`IAM-012`).
9. **Layer 3 Tenancy & Standard CursorPagination:** Layer 3 multi-tenancy derivation from authenticated user in `TenancyMiddleware` + `TenantManager` completely seals cross-tenant visibility (returning 404 for sibling foundation entities). `StandardCursorPagination` enforces `-created_at` ordering across all list endpoints.
10. **Granular Feature Entitlements Hierarchy:** `foundation_entitlements` evaluates per-school overrides before foundation-wide defaults (`IAM-023`). Disabled modules raise HTTP 403 `MODULE_NOT_ENTITLED` (`IAM-024`) via `RequiresModuleEntitlement`, and `GET /api/v1/me` exposes active module flags to hide navigation surfaces dynamically.
11. **Atomic Bulk Import with Exhaustive Diagnostics:** `StudentBulkImporter` validates entire batches across data types, phone numbers, and DB/in-file uniqueness before committing (`spec/02 §8.3`), offering dry-run preview mode (`?dry_run=true`) and returning specific row error lists upon rejection.
12. **Idempotent Gate Ingestion & Debouncing:** Ingestion accepts batches indexed by client `event_uuid` (`HW-005`), filtering rapid repeated scans within `debounce_seconds` (`ATT-007`) and inferring in/out direction automatically for bidirectional turnstiles (`ATT-008`).
13. **Live Gate Console & Edge Synchronization:** Real-time gate monitoring uses cursor-based polling (`ARC-015`, `ATT-013`) by monotonically increasing ID without heavy websocket infra; offline edge devices sync credential whitelists and rules incrementally via timestamp-filtered deltas (`spec/12 §3, §7`).
14. **Multi-Channel Notification Ladder & WhatsApp Gate Alerts:** Inbound gate scans trigger parent arrival WhatsApp messages in < 5s (`ATT-006`). Deduplication prevents re-notifying on debounce (`NTF-003`, `ATT-007`), quiet hours defer non-critical messages (`NTF-002`), emergency alerts bypass restrictions (`NTF-013`), and provider outages automatically cascade across fallback channels (`WHATSAPP` -> `PUSH` -> `SMS` -> `EMAIL`, `NTF-006`).
15. **Gapless Invoice Numbering & Idempotent Generation:** Invoices use sequential per-school per-year counters (`InvoiceNumberSequence`) allocated via `SELECT ... FOR UPDATE` (`FIN-004`). Monthly generation runs are strictly idempotent per `(student, period)`, exclude non-active students (`FIN-005`), calculate explicit IDR `PEMBULATAN` line items (`FIN-008c`), support dry-run previewing (`FIN-008`), and are locked by advisory locks (`ARC-007`).
16. **Payment Webhook Tenancy & Balanced Double-Entry Ledger:** Public webhooks operate without session auth, requiring explicit tenant resolution via `.all_tenants` and `with tenant_context(foundation_id):` to prevent fail-closed query rejection. Payments strictly allocate oldest-first, record partial/full status, hold overpayment as reusable `StudentCreditBalance` (`FIN-015`), and post balanced double-entry `ledger_entries` (`sum(debit) == sum(credit)` per journal per currency to 0.00) using the standard Chart of Accounts (`FIN-021`, `FIN-022`, `CUR-020`).
17. **Academic Core: Weighted Grading & RBAC Reuse:** `AcademicYear`/`Term`/`ClassEnrollment` were net-new (spec/04 referenced `academic_year_id`/`term_id` without defining owning entities); scoped under `apps.academic` rather than `identity` since they're academic-specific. Final term grade (`ACD-008`) is a weighted average of individual published assessments (not category-level) restricted to `SUMMATIVE`/`EXAM`/`PROJECT` types, whose weights must sum to exactly 100% at computation time or raise `WEIGHT_CONFIG_INCOMPLETE`; a counted assessment missing a student's score returns `INCOMPLETE` rather than treating it as zero (`ACD-009`). Reused existing `grades.read`/`grades.write` RBAC permission keys (already present in `ROLE_PERMISSIONS`) instead of minting new ones. Grade-change audit trail (`ACD-005`) relies on `AuditEvent.diff` for before/after retrieval rather than a separate revision table, consistent with finance's correction pattern.
18. **Timetable Conflict Detection Scope:** `TimetableSlot` is keyed off `class_subject` (which already carries `class_group` + `teacher`) rather than duplicating both FKs as spec/04's entity list literally shows, avoiding a drift-prone redundant field. `ACD-017` conflict checks (class/teacher/room double-booking) run at slot-creation time scoped to `(day_of_week, period_no)`; no separate `PeriodGrid`/break-slot config entity was introduced (`ACD-018`) — period grid is currently just a free `period_no` integer per school, deferred until a real per-school grid config is needed. Substitute notification delivery (`ACD-019` "notify the substitute") is deferred: wiring a new `NotificationCategory` + approved template into the existing `notifications` app was judged out of scope for this slice; substitutions persist and are audit-logged only.
19. **Online Exams: Server-Side Timing & Deferred Client Enforcement:** `ExamAnswer` is net-new (not in spec/04's entity list) — required to persist per-question answer state for resume-after-disconnect (`ACD-021`); one row per `(attempt, question)`, upserted on every autosave. `compute_remaining_seconds` derives strictly from `started_at + duration_min`, clamped to `window_end` — client-submitted timestamps are never trusted (`ACD-022`). Auto-grading (`ACD-023`) dispatches by `ExamQuestion.type`: MCQ/TRUE_FALSE exact-match, SHORT case/whitespace-normalized match against an accepted-answers list, MATCHING exact-pairs match, MULTI supports optional partial credit (`(correct_hits - wrong_hits)/len(correct)`, floored at 0); ESSAY always routes to `grading-queue` for manual scoring, and `final_score` stays `None` until every ESSAY answer in the attempt is graded. `shuffle`/`one_question_at_a_time`/`block_back_navigation`/`full_screen_lock` (`ACD-024`) are stored in `Exam.settings` and the per-attempt question order is shuffled server-side and returned in `question_order`, but client-side enforcement (lockdown UI, back-navigation blocking) is out of scope for this backend-only repo — no frontend exists yet. `focus_loss_count` is an unbounded counter, never auto-punitive. Late submissions (`ACD-025`) are handled by `auto_submit_if_expired`, called on every read/write path against an attempt, which finalizes with whatever answers were persisted (no answers lost). 300-concurrent-student load testing (`ACD-026`) has no supporting infra in this repo and was not attempted.
20. **Report Cards: PDF Fallback & Arrears Gate:** `render_report_card_pdf` lazily imports `weasyprint` and falls back to writing plain HTML (`.html` `pdf_key` instead of `.pdf`) when weasyprint's native libraries (pango/cairo/gobject) aren't installed — true in this dev/CI environment despite `weasyprint` being a listed dependency, since those are system libraries pip cannot install. The rendered layout itself is a minimal functional template, not the branded design — spec/appendix's open decision #6 ("Report Card Template: exact layout and signed sample needed") is still unresolved. `ReportCard` uses `(student, term)` uniqueness scoped by `is_current`; `revise_report_card` only fires on a `PUBLISHED` card, flips `is_current=False` on the old row (kept immutable, status stays `PUBLISHED`) and creates a new `version+1` `DRAFT` row — satisfying `ACD-016`'s "corrections create a new version with a visible revision number" without ever mutating a published PDF. `ReportCardPolicy.block_rapor_on_arrears` (default off) reuses `Invoice.is_overdue` from `apps.finance` rather than re-deriving overdue logic; `get_visible_report_card` is the single gate both a future parent-app endpoint and `StudentReportCardView` call — parents never see anything but `PUBLISHED` + non-arrears-blocked cards (`ACD-013`/`ACD-014`). Guardian/parent-authorization filtering (verifying the caller is actually that student's parent) is deferred — out of scope for this backend-only repo, consistent with the parent mobile app being a separate, not-yet-built surface.
21. **Homework: File Metadata Only, No Upload Pipeline:** Consistent with `Student.photo_key`/`Person` PII vault's existing pattern of storing filesystem-path strings rather than binary blobs, `HomeworkSubmission.files` is a `JSONField` list of `{key, filename, size, content_type}` metadata dicts — no multipart upload endpoint exists yet anywhere in the repo, so actual file storage is deferred until one is built. `ACD-027` limits (≤5 files, ≤20MB each, pdf/jpg/png/docx only) are validated against this metadata in `validate_submission_files`. A resubmission is `update_or_create`d onto the same row (one `HomeworkSubmission` per `(homework, student)`) rather than versioned. `remind_unsubmitted` (`ACD-030`) enforces the 12h rate limit via `Homework.last_reminded_at` and computes the unsubmitted roster from `ClassEnrollment`, but — like TASK-024's substitution notification — does not actually send anything. Note: `NotificationCategory.HOMEWORK` already exists in `apps.notifications` (unused until now), so wiring `ACD-029`/`ACD-030` delivery mainly needs a seeded, approved `NotificationTemplate` row for a homework-assigned/reminder key, not a new category — smaller lift than TASK-024's substitute-notification gap; still deferred here to keep this slice scoped to the academic domain.
22. **Teacher Suite: Backend-Only Slice, Notion Open-Item Backlog for the Rest:** `PeriodAttendance` (per-timetable-slot, teacher-submitted) lives in `apps.attendance`, not `apps.academic` — it's attendance-status data, that app's responsibility — and references `apps.academic.TimetableSlot` via a string FK (`'academic.TimetableSlot'`) to avoid a module-level circular import (mirrors the existing `apps.academic` -> `apps.finance` lazy-import precedent for the arrears gate). It is intentionally a separate model from the gate-derived `AttendanceDay`: different granularity (per-period vs whole-day) and different source of truth. `submit_period_attendance` defaults every enrolled student to `HADIR`, pre-fills `ALPA` from that day's `AttendanceDay` (tagged `source=GATE_PREFILL`) unless the teacher supplies an explicit exception, and is idempotent via `update_or_create` on `(student, slot, date)`. Per the SOP update requiring every open item to get its own Notion `[Open Item]` task immediately (not just prose in a PR body), the much larger UI/mobile/behaviour-points/lesson-plans/broadcast portions of `spec/09-teacher-suite.md` were deliberately NOT built here and are tracked individually in Notion rather than attempted piecemeal — see the `Astra Educore` Notion database for the full list.
24. **Campus Wallet: Row-Locked Balance, Idempotent Ledger, Self-Healing Nightly Reconcile:** `Wallet.balance` is a derived-and-cached value maintained inside the same DB transaction as every `WalletTransaction` insert, using `select_for_update()` to serialize concurrent mutations on one wallet (`WAL-001`). Idempotency is a unique `(wallet, idempotency_key)` constraint checked *before* the row lock — a replay short-circuits and returns the original transaction, never double-applies (`WAL-003`). Balance is rejected (not clamped) below zero unless a future `allow_overdraft` flag is added (`WAL-004`, not built this slice). `reconcile_wallet_balances` recomputes from `Sum(amount)` over the ledger and reports (never auto-corrects) any mismatch as an incident via `JobRun.error_text`, matching the existing `generate_invoices` cron command's advisory-lock + `JobRun` pattern. `check_spend_allowed` (`WAL-009`-`013`) is deliberately a pure read function with no POS caller yet — built now so it's unit-tested and ready the moment `[Open Item] POS Terminals` lands. `WAL-007` (auto-freeze wallet on student status change) was NOT wired: `Student.transition_status` emits a `DomainEvent` but nothing subscribes to it generically (existing consumers are called directly, not via a dispatcher), and wiring `apps.identity` to know about `apps.wallet` would invert the dependency direction — tracked as its own `[Open Item]` rather than forced in.
25. **POS Checkout: Online-Only Path, Rejected Sales Still Logged:** `process_pos_transaction` is NOT wrapped in `@transaction.atomic` at the top level — only the inner `record_wallet_transaction` call is — specifically so that when the wallet debit raises (insufficient balance, spend-rule violation), the `POSTransaction` row created in the `except` block to log the rejection (`WAL-013`, "a rejected transaction MUST be logged") survives instead of being rolled back with everything else; wrapping the whole function in one atomic block was tried first and silently discarded the rejected-transaction log on every rejection path (caught by this task's own test suite). `total` charged to the student equals `subtotal` — `commission` is recorded on the transaction (`WAL-021`) as bookkeeping for a future settlement run, not an added fee. `void_pos_transaction` reverses via a `REFUND` ledger entry keyed off `client_transaction_id` (idempotent), and only within `DEFAULT_VOID_WINDOW_MINUTES` (15).
26. **Merchant Settlement: Idempotent Re-run While PENDING, Locked Once PAID:** `run_merchant_settlement` aggregates `Sum(total)`/`Sum(commission)` over `COMPLETED` `POSTransaction` rows only (VOIDED excluded) for `[period_start, period_end]`; re-running for the same `(merchant, period)` while still `PENDING` updates the existing row in place (so a same-day correction doesn't create duplicates), but once `mark_settlement_paid` has run, re-running raises `SettlementStateError` — mirrors the DRAFT-only-regenerates pattern from `ReportCard` (TASK-027). `generate_settlement_statement_pdf` reuses the exact weasyprint-with-HTML-fallback pattern from report cards verbatim (same missing native-library situation in this dev/CI environment). Merchant/product permission checks for `sales`/`settlements`/`run_settlement` use `finance.payment.read`/`write` (not `school_config.*`, which `finance_officer` lacks) — caught by this task's own API tests returning 403 before the fix.
27. **POS Offline Sync: `allow_negative` Is a Deliberate, Opt-In Escape Hatch:** `record_wallet_transaction` gained an `allow_negative` parameter used ONLY by the offline batch path (`process_offline_pos_batch`) — the online checkout path from TASK-032 is untouched and still hard-rejects any transaction that would go negative. When a negative balance is accepted, the ledger line is stamped `WalletTransactionStatus.RECONCILE_REQUIRED` (not `COMPLETED`) and `Wallet.requires_reconciliation` flips true; both `check_spend_allowed`'s daily-limit aggregation and `reconcile_wallet_balances`' drift computation had to be updated to include `RECONCILE_REQUIRED` alongside `COMPLETED` in their sums, or a caught-by-tests bug would have made every offline overspend look like phantom balance drift the very next night. `WAL-016`'s `offline_floor_limit` (default Rp 50,000/day/student) is checked and enforced as a hard reject *before* the wallet debit is even attempted — a structurally different, stricter gate than the balance check, since it caps offline risk regardless of how much money is actually in the wallet. `pos_session`/`pos_sync` mirror the existing `apps.hardware`/`apps.attendance` edge-device sync pattern almost verbatim (`updated_at`-filtered deltas, `next_cursor` = server time) rather than inventing a new sync protocol. Guardian notification when `requires_reconciliation` is set (`WAL-017`'s \"notifying the guardian\") is still not wired — logged as its own `[Open Item]`, the same recurring notification-template gap as TASK-024/025.
28. **Wallet Reconciliation Notice: Closes the WAL-017 Gap via a New Category, Not a New Dispatcher:** Sourced from a Claude Design import (`spec/17-wallet-reconciliation-notice.md`, `REC-001` to `REC-032`) fetched via the `DesignSync` MCP tool after `/design-login` authorization — read the full spec before implementing, not just the visual mockup. `WalletReconciliation` (one `OPEN` row per accepted overspend, `REC-001`/`REC-004`) is created and the combined-shortfall notice queued inside the *same* `transaction.atomic()` block as the wallet debit and `POSTransaction` insert in `process_offline_pos_batch` — satisfies "same transaction, no row no debt" without threading a `pos_transaction` param through `record_wallet_transaction` (which doesn't have one yet at debit time; the POS row is created after). Settlement (`REC-005`/`006`) is evaluated inside `record_wallet_transaction` itself whenever a mutation brings the balance back to ≥0, not by a sweep — mirrors the same "evaluated inside the wallet-mutation transaction" principle already used for offline overspend acceptance. **Send-time re-evaluation (`NTF-004`/`REC-008`) had no existing generic mechanism to hook into** — `dispatch_intent`'s `condition_validator` parameter exists but was never wired to anything, and grepping for `FIN-027` (the spec's own cited precedent, "a paid invoice cancels its pending reminder") found no implementation anywhere in the repo. Rather than build a generic condition-validator dispatcher (its own multi-app undertaking), added three narrow, category-gated special cases directly in `apps.notifications.services.process_intent` (cancel-if-settled check, SMS excluded from the fallback ladder per `REC-019`, `notice_sent_at` stamped on successful dispatch) — each lazily imports `apps.wallet`, mirroring the existing `apps.attendance` → `apps.notifications` lazy-import precedent, just in the other direction. A generic `NTF-004` dispatcher is logged as its own `[Open Item]` rather than built speculatively for one caller. Deferred to a follow-up task: the 48h reminder cron (`send_wallet_recon_reminders`, `REC-012`), the 7-day invoice-handover cron (`invoice_stale_reconciliations`, `REC-013` — needs a new `apps.finance` ad-hoc invoice-line helper that doesn't exist yet), the bendahara admin queue API (`REC-025` to `REC-029`), and reporting (`REC-030`-`032` — `refresh_reporting` is itself an unbuilt crontab placeholder, like `run_arrears_ladder`).
29. **Reconciliation Reminder & Invoice Handover: Append-Don't-Duplicate Invoicing:** `Invoice` has a unique-active-invoice-per-(student, period) constraint, so `REC-013`'s "posted to the student's next invoice" could not mean creating a fresh invoice unconditionally — `add_adhoc_invoice_line` (new, `apps.finance.services.invoicing`, re-exported from `apps.finance.services`) appends an `InvoiceLine` to the student's most recent open invoice (`DRAFT`/`ISSUED`/`PARTIALLY_PAID`) when one exists, manually incrementing `subtotal`/`total` since those are denormalized fields `InvoiceLine` doesn't auto-sync; only creates a minimal new invoice when none is open. The 48h reminder and 7d handover are both evaluated **per `WalletReconciliation` row** off that row's own `notice_sent_at`/`detected_at`, not per wallet — `get_wallets_due_for_reminder` groups eligible rows by wallet only to dedupe the *notification* (one combined reminder), while `reminder_sent_at` is still stamped per-row. Reminder eligibility hard-requires `notice_sent_at IS NOT NULL` (`REC-029`) — a case whose initial notice never delivered on any channel is permanently excluded from the 48h clock until TASK-035's `mark_reconciliation_notice_sent` eventually stamps it (if ever). `wallet.recon.invoiced` dispatches under `NotificationCategory.PAYMENT_DUE`, not `WALLET_RECONCILIATION` — spec/17 §5's template table marks it as the explicit handover point into the existing arrears ladder, so it inherits `PAYMENT_DUE`'s opt-out/digest/rate-limit rules from that point on, not the wallet-specific ones.
30. **Reconciliation Admin Queue: Write-Off Needed `allow_negative`, Caught by Its Own Test:** `write_off_reconciliation_case` restores only the ONE case's `shortfall` to the wallet balance via `record_wallet_transaction(..., allow_negative=True)` directly (not `adjust_wallet`, which doesn't expose that param) — a partial write-off while other `WalletReconciliation` rows for the same wallet are still genuinely `OPEN` legitimately leaves the wallet negative, and the first version of this code called `adjust_wallet` without `allow_negative`, which raised `InsufficientBalanceError` on exactly that case (caught by `test_write_off_does_not_settle_other_open_cases`, which had to be rewritten to trigger a second *real* overspend via `process_offline_pos_batch` rather than fabricating an ORM-only `WalletReconciliation` row — a debt row with no matching wallet transaction doesn't exercise the real settle-vs-leave-open branch). The case is marked `WRITTEN_OFF` *before* the wallet adjustment runs specifically so it's excluded from `settle_reconciliations_for_wallet`'s bulk `OPEN`→`SETTLED` sweep if the adjustment happens to bring the balance back to ≥0. `get_notice_delivery_receipt` (REC-027) has no dedicated FK from case to intent — it re-derives the same `dedupe_key` format TASK-035 already mints and looks the `NotificationIntent` up by that. "Resend notice" mints a fresh per-call `dedupe_key` (`wallet_recon_resend:{wallet_id}:{timestamp}`) and passes `immediate=True` specifically so `dispatch_intent`'s own dedup logic doesn't silently return the original (likely-failed) intent instead of actually resending.
31. **Wallet Auto-Freeze: First Direct Call FROM `apps.identity` INTO a Leaf App:** Every prior cross-app call in this codebase went leaf-to-leaf (`apps.attendance` -> `apps.notifications`, `apps.academic` -> `apps.finance`/`apps.notifications`, `apps.wallet` <-> `apps.notifications`) or read-only imports of `apps.identity` models. `sync_wallet_freeze_on_student_status_change` is the first case of `apps.identity` — the most foundational app, depended on by nearly everything — making an outbound call into a leaf app (`apps.wallet`). Kept safe the same way as every other cross-app side-effect call in this repo: lazy import inside the method body (no module-level dependency), wrapped in `try/except` so a wallet-side exception can never prevent the core `Student.transition_status` write from committing (verified by its own test, which monkeypatches the wallet function to raise and confirms the student status still transitions). Only acts on a wallet that already exists — no auto-provisioning on freeze. Unfreezes symmetrically on return to `ACTIVE` (spec only mandates the freeze direction) but doesn't distinguish manual-vs-auto-frozen wallets, so a manually-frozen wallet would also auto-unfreeze on reactivation — a documented simplification, not exercised by any current caller since no manual-freeze admin action exists yet either.
32. **Wallet Refund on Exit: Closure Deliberately Bypasses the Normal Ledger Path:** `_close_wallet_with_transaction` does NOT go through `record_wallet_transaction` — it directly locks the wallet, zeroes the balance, and sets `status=CLOSED`, because TASK-038's auto-freeze fires on the exact same `GRADUATED`/`TRANSFERRED_OUT` transition that creates the `WalletRefundRequest`, so by the time a bendahara resolves it the wallet is already `FROZEN` and `record_wallet_transaction`'s ACTIVE-only check would reject the payout outright — confirmed by `test_mark_paid_zeroes_balance_and_closes_even_though_frozen`, which starts from a wallet TASK-038 has already frozen via a real `transition_status` call. `queue_wallet_refund_on_exit` is wired into `Student.transition_status` as a SECOND, independently try/except-wrapped call alongside TASK-038's freeze sync (not combined into one call) — a failure in one must never block the other, since they're two unrelated obligations that happen to share a trigger. `mark_refund_donated` has no default-consent path — `donation_consent` must be explicitly `True` in the call, matching WAL-026's \"MAY be donated... only with explicit guardian consent.\" WAL-027 (\"never auto-forfeited\") required no code at all beyond restraint: no cron, no scheduled command, nothing anywhere touches a `PENDING` `WalletRefundRequest` — it simply persists until a human resolves it.
33. **Wallet VA/QRIS Top-up: Parallel Intent Model, Not a `PaymentIntent` Generalization:** Investigated reusing `apps.finance`'s gateway stack directly rather than reimplementing it. ## 6. Retrospectives (continued)

54. **Notification Template Seed Decision — Keep ANNOUNCEMENT Category, Don't Proliferate:** The open item asked whether `academic.permission_slip.new` should get its own `NotificationCategory` or reuse the existing `ANNOUNCEMENT`. Kept `ANNOUNCEMENT` — semantically, a permission slip request *is* a school announcement to guardians, and the existing category config (WHATSAPP+PUSH, opt-out allowed, NORMAL priority) fits perfectly. A new category would only add unnecessary proliferation; if separate opt-out control is ever needed, one can be added then. The dispatch payload was also enhanced with structured fields (`title`, `class_group_name`, `event_date`, `location`) alongside the existing pre-formatted `message` — so seeded templates can reference structured variables rather than relying on the generic fallback's `{message}` key.
55. **Parent Messages Tab — Missing Guardian-Facing Broadcast Endpoint Was the Only Backend Gap:** The spec described the Messages tab as three types of content (announcements, teacher messages, permission slips), but "teacher messages" are structurally just broadcasts (class-group-wide announcements from teachers). The `BroadcastViewSet` was staff-only (`grades.read`), so no guardian-facing list existed. A single new view (`StudentBroadcastView`) following the exact same pattern as `StudentPermissionSlipView` (guardian access check via `can_guardian_access_student`, class group resolution from active `ClassEnrollment`) closed the gap. The mobile screen used a segmented-control approach (Pengumuman | Izin tabs) rather than a unified chronological feed — broadcasts are read-only cards without actions, while permission slips have a sign modal with typed signature, making a single mixed list confusing. The tabbed layout keeps both surfaces clean.
56. **Full App-Wide i18n Propagation — Pre-bound Translation Hook and Domain Namespacing:** PAR-014 requires instant runtime language switching across every tab without reload or reinstall. Standardized on exporting a pre-bound `t: (key: string, defaultText?: string) => string` helper from `useLocale()`, so screens invoke `t('key')` cleanly without passing `locale` to every translation call while preserving access to raw `locale` for `toLocaleDateString(locale, ...)`. Formatted the static string dictionary with structured dot namespaces (`tab.*`, `common.*`, `attendance.*`, `academic.*`, `wallet.*`, `nutrition.*`, `invoice.*`, `payment.*`, `messages.*`, `slip.*`, `day.*`, `banner.*`) and guaranteed graceful two-level degradation (`en-US` -> `id-ID` -> `defaultText`/key).
57. **Calendar Academic Mapping — Dated-Event Bridging & Attendance Exemption Invariants:** `TimetableSlot` is an undated weekly recurring grid (`day_of_week`, `period_no`), so dated events (holidays, exam windows, ad-hoc cancellations) could not be mapped directly into slot rows. Built `AcademicCalendarEvent` as the dated event store bridging external calendar pulls to academic operations. Applied two critical architectural guardrails: (1) Strict opt-in: `auto_sync_enabled` and `auto_create_exams` default to `False` in `CalendarAcademicSyncPolicy` — external pulls never mutate academic records or create exams without explicit policy opt-in; (2) Timetable attendance exemption: `get_teacher_agenda` and `get_expected_periods_for_school` dynamically query overlapping `AcademicCalendarEvent(affects_attendance=True)` on the target date, annotating slots with `is_exempt=True`, `exemption_reason`, and excluding exempt slots from `missing_only=True` to prevent false missing-attendance alerts for teachers and school admins.
58. **Marketing Landing EN Toggle — Was Decorative, Now Real Django i18n (Scoped, Not Global):** The public marketing site's ID/EN toggle (built in TASK-091) was always a hardcoded `<span>ID</span><span>EN</span>` with a tooltip stating English wasn't built — reported as "landing EN does not work" and fixed rather than left as a known gap, per explicit user request. Wired `LocaleMiddleware` + `LANGUAGES` + the `i18n` context processor + `django.conf.urls.i18n`'s `set_language` view, scoped so only `apps.marketing`'s templates/`gettext_lazy`-wrapped strings actually vary by language — no `i18n_patterns` URL-prefixing, so `/api/v1/*` and every other route is untouched. Filled and compiled 179 English translations into the pre-existing (but previously unused-by-marketing) `locale/en/LC_MESSAGES/django.po`; committed the compiled `.mo` alongside it since no deploy step runs `compilemessages`. One real bug caught mid-build: `RELEASES[].support` was a translated label the template compared against the Indonesian literal `'Aktif'` for EOL styling — that comparison would've silently broken under English, so split it into a separate plain `support_active` bool. PR: [#142](https://github.com/wsoontornsanee/educore/pull/142), merged 2026-09-18.
59. **Staff Role Grant/Revoke — JSON API Parity, Session-Staff Only (Product Decision Confirmed):** PR #223 shipped role editing for the web console only; whether to expose it over the API at all was flagged as an open product decision (widens the surface for the most privilege-sensitive write in the system) rather than built inline. User confirmed: yes, but session/JWT-authenticated staff only — never partner API keys (the repo has no API-key authentication wired into `apps/identity`'s URLs at all, so this is the natural default, not an added restriction). Added `GET/POST /api/v1/staff/<id>/roles/` and `DELETE /api/v1/staff/<id>/roles/<assignment_id>/` (`apps/identity/views.py`: `StaffRoleListView`, `StaffRoleDetailView`) as thin wrappers that call the existing `role_admin.grant_role` / `revoke_role_assignment` service functions directly — zero policy duplication, identical escalation rules (self-edit, scope ceiling, no-escalation, last-foundation-admin guard) enforced exactly as on the console. `RoleChangeError` maps to 400; out-of-ceiling/other-tenant staff is 404 before the grant/revoke logic even runs. New `apps/identity/tests/test_role_api.py` (18 tests) covers auth/permission rejection, the school ceiling, and the same escalation scenarios as `test_role_admin.py` at the API layer. No OpenAPI/schema tooling exists in this repo to regenerate.
60. **Canteen QR Charge — Offline-Terminal-Minted Tokens, Backend Slice Only (QRS-022/023):** No local spec text exists for QRS-022/023 (the source is an external Claude.ai design-project doc, not checked into this repo) — designed against the Notion task's one-line goal plus existing codebase conventions instead. Reused, rather than invented, three existing patterns: (1) `apps/partners/crypto.py`'s Fernet-at-rest secret pattern, copied verbatim into new `apps/wallet/crypto.py` with its own `EDUCORE_WALLET_FERNET_KEY`; (2) the online QR session's "no amount/student encoded in the token" invariant (`qr_charge.py`), carried into the offline token shape — it only proves "a real, paired terminal minted this single-use session," never the sale itself; (3) the existing idempotent `process_offline_pos_batch` ingest path, extended with an optional `qr_token` per transaction rather than a new sync endpoint — `POSTransaction.qr_offline_nonce` gets its own `UniqueConstraint` per terminal, exactly mirroring how `client_transaction_id` already dedupes retried syncs (WAL-015: two independent replay defenses, one per concern). Key rotation was a genuine open design fork (confirmed with user): a revoked `POSTerminalSessionKey` stays valid for **verification only** (never new minting) for a 7-day grace window, so an offline sale signed before rotation still syncs cleanly instead of getting stuck. Token expiry is checked against the sale's own `occurred_at` (the terminal's local clock at scan time), never against wall-clock "now" at sync time — syncing days later must not retroactively invalidate a legitimately-scoped offline sale. New `POSTerminalSessionKey` model + `apps/wallet/qr_offline.py` (mint/verify/issue/revoke) + two new `POSTerminalViewSet` actions (`session-key/issue`, `session-key/revoke`, `hardware.write`). Deliberately NOT in this slice, logged as a separate Notion Todo: the React Native terminal client itself (the wire format is fully documented in `qr_offline.py`'s docstring for whoever builds it). 17 new tests (`test_offline_qr_tokens.py`); full `apps.wallet` (299) + `apps.partners` (362 combined) pass.
61. **Reconciliation AMOUNT_MISMATCH — Signed StudentCreditBalance, Not a Silent Write-Off (spec/06 FIN-024):** The open item asked what should happen when a gateway settlement's actual amount differs from what EduCore billed. User's design decision, confirmed directly (no external accounting sign-off needed): both directions land on the student's `StudentCreditBalance` (`apps/finance/models.py:489`), made signed rather than a new concept — positive auto-sweeps the student's other open invoices (remainder stays as credit); negative raises a one-time alert, never silent. The invoice/AR side is untouched by the gateway variance — it still settles at the system/billed amount, so a student's invoice history never reflects what a bank transfer happened to be short or over by. Cash/Bank instead books the gateway's *actual* net (best-practice: matches the bank statement), and the resulting gap is what moves the signed balance — `post_payment_settlement_journal`'s `overpayment` param renamed to `credit_balance_delta` (signed; Cr 2200 if positive, Dr 2200 if negative) across all 3 call sites, `_finalize_payment_settlement` gained an optional `reconciliation_delta` (default 0, so every other settlement path — webhook, cash desk, manual transfer approval, matched auto-settle — is untouched). New `apply_student_credit_to_invoices` (`payments.py`) sweeps a credit balance across open invoices oldest-first *without* fabricating a `PaymentAllocation` (that FK requires a real `Payment`, and there isn't one for an existing credit being applied) — instead it's its own honest ledger event (Dr 2200 / Cr AR, `ref_type='CREDIT_APPLICATION'`). Negative-balance alert reuses the existing `PAYMENT_DUE` notification category (a new template key, not a new category — matches retrospective #54's don't-proliferate-categories precedent) via the same guardian-resolution pattern `arrears.py` already uses. One real bug caught before merge: `PaymentDiscrepancy.gateway_net` is a stored *display* snapshot, not guaranteed consistent with `gateway_amount - gateway_fee` at resolution time (a test fixture that never set it proved this — defaults to 0, silently unbalancing the journal) — fixed by computing net inline from `gateway_amount`/`gateway_fee` instead of trusting the stored field. 13 new tests (`test_reconciliation_amount_mismatch_balance.py`); full `apps.finance` suite passes at the same 2 known-preexisting failures as clean `main` (`test_api_cancel_and_write_off`, `test_discount_approval_action`).
